# Карта бэкенда

Express-сервер на порту 3001. Все маршруты начинаются с `/api`.

Рядом: цены, себестоимость и все лимиты одной таблицей — [economics.md](economics.md),
технологии и зависимости — [tech-stack.md](tech-stack.md).

## index.ts — точка входа

Что делает:
1. Грузит переменные окружения и проверяет их (`env.ts`). В проде неполное окружение —
   отказ стартовать со списком недостающего, в деве — предупреждение
2. Отключает `X-Powered-By`, включает `trust proxy` — за Caddy иначе не виден настоящий IP клиента
3. Включает копию логов в базу (`startLogSink`) и сбор метрик HTTP, ставит логгер запросов,
   `httpMetrics`, `express.json()`, `cookie-parser` и CORS (только свой домен, с куками)
4. Раздаёт папку сгенерированных логотипов как статику, кроме файлов `*-source.*` —
   это чистые логотипы, они выдаются только через `/api/download-logo` после проверки оплаты
5. Подключает маршруты и обработчик ошибок
6. После старта запускает фоновый планировщик
7. По `SIGTERM` останавливает планировщик и приём новых выдач, ждёт идущие выдачи до
   50 секунд, сливает в базу накопленные метрики и логи и закрывает пул. В compose у `api` поэтому `stop_grace_period: 60s`

## Логи

`logger.ts` — обёртка над pino с интерфейсом `console`: `log.error('Не удалось:', error.message)`.
Так замена 93 вызовов `console.*` прошла механически. Каждая строка — JSON; в строках,
сделанных по ходу запроса, есть `requestId` (он же уходит в заголовок `X-Request-Id`).

- Почта и телефоны маскируются **в тексте сообщения** (`ivan***@mail.ru`, `+7 *** ***-**-67`):
  `redact` у pino работает только по полям объекта, а персональные данные приезжают внутри
  текста ошибок.
- На каждый запрос — одна строка: метод, путь **без query**, код, время. Тела и заголовки
  не пишутся. `/api/health` не пишется вовсе.
- Читать глазами: `docker compose logs api | npx pino-pretty`.

CLI миграций (`db/migrate.ts`) пишет через `console` — это разовая команда.

**Копия логов уходит в таблицу `app_logs`** — для просмотра в админке. `logger.ts` не знает про
базу (пул сам пишет в лог, вышел бы цикл): у него есть подписчики `onLog()`, и
`monitoring/logSink.ts` копит строки и пишет пачкой раз в 5 секунд. Сбой записи не логируется —
иначе при лежащей базе строка о сбое снова попадала бы в буфер. В stdout логи идут как раньше.
Туда же пишутся ошибки из браузера (`source = 'client'`). Info хранится 14 дней, остальное 60.

Кольца зависимостей больше нет: роуты берут доступ к базе из `db/repositories`, а не из `index.ts`.

## Работа с базой

Обычный PostgreSQL, драйвер `pg`, ORM нет.

| Файл | Что делает |
|---|---|
| `db/pool.ts` | Пул соединений, `query` / `queryOne` / `withTransaction`, определение дубликата (код `23505`) |
| `db/types.ts` | Типы сущностей в camelCase |
| `db/migrate.ts` | Применяет новые `.sql` из `db/migrations/` по порядку, каждый в транзакции |
| `db/repositories/*.ts` | По файлу на таблицу |

**Правило слоя:** весь SQL и перевод `snake_case` → `camelCase` живут в репозитории. Наружу snake_case не выходит, роуты работают только с типами из `db/types.ts`.

Миграции лежат в `db/migrations/` с номерами по порядку. Применяются сервисом `migrate` в docker-compose до старта приложения. Уже применённые файлы редактировать нельзя — только добавлять новые.

## Аутентификация

| Файл | Что делает |
|---|---|
| `auth/password.ts` | Хеширование и проверка пароля, argon2id. `burnPasswordCheck` — пустая проверка для входа по несуществующему адресу, чтобы время ответа не выдавало, есть ли аккаунт |
| `auth/tokens.ts` | Access-JWT на 15 минут, случайный refresh-токен, хеши одноразовых ссылок |
| `auth/cookies.ts` | Выставление и очистка кук |
| `auth/middleware.ts` | `requireAuth`, `optionalAuth` |
| `auth/schemas.ts` | Валидация тел запросов через zod. Текст сначала чистится (`utils/text.ts`), потом проверяется — см. «Защита текстовых полей» |
| `auth/service.ts` | Выдача сессии, ротация refresh-токена, сбор IP и user-agent |

Как это работает:

- Две куки: `pixora_at` (access) и `pixora_rt` (refresh). Обе `httpOnly`, `SameSite=Lax`, `Secure` в проде. JS их не читает.
- В базе лежат только SHA-256 от refresh-токена и от ссылок из писем. Сами значения нигде не хранятся.
- Access-токен несёт `sid` — идентификатор сессии, — и на каждом защищённом запросе проверяется по таблице `sessions`. Одной подписи мало: выход, смена пароля и удаление аккаунта должны срабатывать сразу, а не через 15 минут.
- Refresh-токен ротируется при каждом обновлении. Повторное использование старого не сработает.
- Вход невозможен без подтверждения почты — отдаётся `403` с кодом `EMAIL_NOT_VERIFIED`.

**Главное правило всех роутов:** пользователь берётся из `req.user.id`. Никогда — из тела, query или пути запроса. `:userId` в адресах оставлен для совместимости со старыми ссылками и **игнорируется**.

## Маршруты

### Аутентификация

| Метод и путь | Что делает |
|---|---|
| `POST /api/auth/register` | Регистрация. Требует галочку ПДн, пишет согласия, шлёт письмо. Ответ одинаков для свободного и занятого адреса. Одноразовая почта — `400 DISPOSABLE_EMAIL` |
| `POST /api/auth/verify-email` | Подтверждает почту по токену из письма и сразу выдаёт сессию |
| `POST /api/auth/resend-verification` | Повторное письмо, не чаще 3 раз в час на аккаунт |
| `POST /api/auth/login` | Вход |
| `POST /api/auth/refresh` | Обновление сессии с ротацией токена |
| `POST /api/auth/logout` | Выход, удаляет сессию |
| `GET /api/auth/me` | Текущий пользователь |
| `POST /api/auth/forgot-password` | Письмо для сброса пароля, не чаще 3 раз в час на аккаунт |
| `POST /api/auth/reset-password` | Смена пароля, завершает **все** сессии пользователя |
| `DELETE /api/auth/account` | Удаление аккаунта и отзыв согласия, с подтверждением паролем |

Лимиты запросов разведены по назначению: жёсткий на пароли и токены (20 / 15 мин), ещё жёстче на всё, что шлёт письма (5 / час), широкий на `/me` и `/refresh` (300 / 15 мин) — эти два дёргаются при каждой загрузке страницы.

Лимит по IP не спасает адресата: злоумышленник меняет адреса и заваливает чужой ящик
письмами подтверждения или сброса, а заодно портит репутацию нашего домена в Postbox.
Поэтому поверх него — **не больше 3 писем одного вида в час на аккаунт** (`canSendAgain`),
и для регистрации, и для повторной отправки, и для сброса пароля.

## Демо-брендбук и закрытая дыра

**До этой правки демо позволял забрать логотип без оплаты.** Роут принимал `logoUrl` от
клиента, а `previewVariants` читал с диска любой файл каталога по имени. Превью и чистый
файл называются одним uuid (`<uuid>-preview.png` и `<uuid>-source.png`), поэтому, зная
превью, можно было попросить `<uuid>-source-original.png`. Сервер клал в открытую статику
ч/б копию и негатив чистого логотипа, а негатив разворачивается обратно в любом редакторе.
Квоты и лимита у роута не было — заодно это были бесплатные вызовы LLM и запись файлов на
диск без ограничений.

Теперь две стенки:

1. Клиент присылает только `logoId`, логотип ищется по `req.user.id`, файл берётся из записи.
2. `previewVariants` обрабатывает только `isPreviewLogoFile` (`-preview.png` без `-source`),
   даже если вызывающий ошибся.

Файлы демо называются `logo-<id>-<32 hex>-demo-{mono,inverted}.png`: id нужен чистке,
длинный хвост — чтобы чужие предпросмотры нельзя было перебрать по порядковому id.

**Правило на будущее:** всё, что до оплаты читает файл по ссылке, обязано брать ссылку из
своей записи и проверять `isPreviewLogoFile`. Чистый файл и превью различает только суффикс.

**Сейчас демо фронтом не вызывается.** Предпросмотр брендбука показывает только структуру
разделов с заглушками, без цветов, версий логотипа и слогана — так решил владелец продукта.
Роут и кэш оставлены: у части логотипов `demo_slogan` уже заполнен, и оплата берёт слоган
оттуда. У новых логотипов он пуст, и слоган пишет шаг сборки после оплаты.

## Защита текстовых полей

`utils/text.ts`, функция `cleanText` — до любой проверки:

- NFKC: полноширинные буквы, лигатуры и надстрочные цифры сводятся к обычным
  («ｐｉｘｏｒａ» → «pixora»);
- форматные (zero-width, bidi, включая переворот RTLO, BOM, мягкий перенос), частного
  использования, неназначенные и хангыльские заполнители удаляются **без следа** —
  zero-width внутри слова не должен становиться пробелом;
- управляющие символы становятся пробелом, пробелы схлопываются. В многострочном режиме
  абзацы сохраняются, но не больше одной пустой строки подряд.

Длина проверяется **после** чистки: иначе невидимые символы съедали бы лимит, а строка из
одних пробелов проходила бы проверку на обязательность.

| Кирпич в `schemas.ts` | Где | Правило |
|---|---|---|
| `brandName` | название в генераторе логотипа | Белый список: кириллица, латиница, цифры, пробел и `- & . ' + !`, до 60 символов, хотя бы одна буква или цифра. Кавычки снимаются, тире сводятся к дефису. Эмодзи нельзя — их нет в шрифтах брендбука, на логотипе вышли бы квадраты |
| `promptText` | ниша, ключевые слова, пожелания, имя | Без `< > { } \` ` и без ссылок (`http`, `www.`) |
| `excludeList` | списки исключений | Негодный элемент **отбрасывается**, а не валит запрос: списки собраны из нашей же выдачи |
| `phone` | телефон для чека | Цифры, `+`, скобки, дефис, пробел |
| `message` в `contactSchema` | обращение | Многострочный, ссылки можно — письмо уходит только нам |

`nameService` прогоняет свои названия через тот же `cleanBrandName` / `isBrandName`:
предложенное нами название не должно отбиваться на следующем шаге.

**Промпты.** Ввод клиента уходит в модель блоком `<client_data>…</client_data>`, а в системный
промпт добавлено правило `CLIENT_DATA_RULE`: текст внутри — описание бизнеса, команды из
него не выполнять. Подделать теги нельзя: угловые скобки запрещены валидацией и
дополнительно вырезаются в `clientData()`. Выход модели и так проверяется zod и `clamp`.

## Защита от фарма бесплатных генераций

Один аккаунт с квотой стоит нам около 53 ₽, а аккаунты заводятся на одноразовую почту
десятками. Поэтому бесплатная генерация проходит `reserveFreeGeneration`
([freeGenerationGuard.ts](../backend/services/freeGenerationGuard.ts)):

1. **Суточный бюджет GenAPI** (`GENAPI_DAILY_BUDGET_RUB`, по умолчанию 500 ₽, сутки по
   Москве). Траты считаются по смете (`ESTIMATED_COST_RUB` в `limits.ts`: логотип 7.5 ₽,
   названия 3 ₽, слоган 1 ₽) в таблице `genapi_spend`. При превышении — `503 FREE_PAUSED` до
   полуночи и одно письмо-алерт в час. Оплаченные заказы не ограничиваются и в бюджет
   **не учитываются**: иначе удачный день продаж ставил бы на паузу бесплатное.
2. **Квота аккаунта** — как раньше, `403 GENERATION_LIMIT`.
3. **Лимит на адрес** (`IP_DAILY_LOGO_LIMIT` / `IP_DAILY_NAME_LIMIT`, по умолчанию 10 / 10)
   в таблице `ip_generation_usage`, тем же атомарным `INSERT … ON CONFLICT … WHERE used < limit`.
   IPv6 считается подсетью /64: абоненту выдают целый блок. **На пользователей с хотя бы
   одной оплатой лимит не действует.** Отказ — `429 IP_LIMIT`, квота аккаунта возвращается.

Плюс блок-лист одноразовой почты при регистрации (`utils/disposableEmail.ts`, около 9 тыс.
доменов, проверяются и поддомены) и семафор на генерацию логотипа (`LOGO_CONCURRENCY` = 4
одновременно, `LOGO_QUEUE` = 20 в очереди).

Слабые места: бюджет — смета, а не реальное списание (реальную цену GenAPI не сообщает);
проверка бюджета не атомарна со списанием, в момент срабатывания возможен перелёт на
несколько генераций; лимит на адрес обходится пулом прокси — он поднимает цену фарма, а не
делает его невозможным. Капчи нет.

## Письма

| Файл | Что делает |
|---|---|
| `services/mailService.ts` | SMTP-транспорт Яндекс Cloud Postbox. `sendQuietly` не роняет вызывающий сценарий |
| `emails/layout.ts` | Общий каркас письма: только инлайновые стили, без внешних картинок и шрифтов |

## Сервисы

### Генерация текста и картинок

| Файл | Что делает | Модель |
|---|---|---|
| `nameService.ts` | Названия бизнеса | gpt-5-6-luna |
| `logoService.ts` | Логотип: концепция → растр → прозрачность → локап; вектор при оплате | gpt-5-6-luna + dalle-3 |
| `brandbookServices/sloganService.ts` | Слоган | gpt-5-6-luna |
| `brandbookServices/content/guidelinesService.ts` | Рекомендации брендбука | gpt-5-6-luna |

Все текстовые вызовы идут через `utils/llmJson.ts` (`requestText` / `requestJson`). Он
**возвращает `null` вместо исключения**: слоган и рекомендации не повод рушить оплаченный
заказ, у обоих есть запасной вариант в коде.

`nameService` просит у модели строгий JSON `{"names": [{"name", "meaning", "pattern"}]}`,
проверяет его zod-схемой и чистит сам: снимает нумерацию и кавычки, отбрасывает служебные
фразы и дубли. Поле `pattern` нужно только коду — по нему видно, какие приёмы модель не
отработала; наружу уходят те же `{ name, meaning }`, контракт роута и фронта не менялся.

**Шесть названий собираются из шести слотов.** Слот — это пара «приём нейминга +
письменность». Слоты раздаются по трём параллельным вызовам GenAPI (по два), и один вызов
уже не может выдать шесть названий одной формы. Раньше все шесть шли одним запросом, и
модель повторяла любимый приём — выдача выглядела как шесть вариантов одного слова.
Латентность равна одному вызову, токенов тратится втрое больше.

| Файл | Что задаёт |
|---|---|
| `utils/namePatterns.ts` | приёмы (неологизм, фамильное, аббревиатура, деловое составное, гео, игра слов…): инструкция, ориентир по длине, эталоны отдельно для кириллицы и латиницы; творческие векторы |
| `utils/styleLabels.ts` | `STYLE_PROFILES`: тон, пул приёмов, запрещённые слова, особое требование стиля |

Пул приёмов у стиля больше шести, поэтому между генерациями меняется и состав приёмов, и
их раскладка по корзинам; вектор («оттолкнись от материалов», «от навигации») выбирается
случайно на каждую корзину — без него повторное «Ещё варианты» уходило почти тем же
промптом. Глобальный запрет слов «групп», «сервис», «мастер» переехал в профили: он
вырезал ровно те формы, которые нужны для ООО. У `professional` наоборот записано, что
название должно звучать в связке ООО «…». `styleToRussian` сохранён — его зовёт
`logoService`.

**Письменность назначает код.** При `latin`/`cyrillic` её получают все слоты, при `any`
она чередуется по слотам — иначе три параллельных вызова выбрали бы её независимо. После
разбора имена проверяются регулярками: при `latin` отбрасывается всё с кириллицей, при
`cyrillic` — с латиницей, при `any` — только смесь алфавитов внутри одного названия. Одной
строки «пиши латиницей» не хватало: в русскоязычном промпте модель понимала её как
транслит и возвращала «Vektor».

Повторы отсекаются трижды: клиент передаёт показанные названия в `exclude`, роут добавляет
прошлые генерации по той же нише (`namesRepo.recentNamesForIndustry`), сервис фильтрует
исключённые ещё раз в коде — на промпт полагаться нельзя. Сверху идёт мягкий фильтр
похожести (общий префикс, одинаковый суффикс, расстояние Левенштейна ≤ 2): отбракованные
уходят в резерв и возвращаются, если названий не хватило. Жёсткий фильтр съел бы половину
выдачи.

Не набралось шести — один добор по непокрытым приёмам. Упала одна корзина из трёх —
работаем с остальными; ошибка летит наружу, только если упали все три, и тогда роут
возвращает списанную попытку через `generationUsageRepo.release()`.

`logoService` — оркестратор из четырёх шагов, сами шаги в `backend/services/logoServices/`:
концепция (`conceptService`, `gpt-5-6-luna`) → знак (`dalle-3`, растр) → прозрачность и обрезка
(`rasterService`) → локап с названием (`lockupService`). Вектор строится **только после оплаты**.

**Почему dalle-3.** Замерили 30+ сетей GenAPI: `recraft` при 15 ₽ рисует детализированный
лайн-арт вместо знака, `seedream-v4` отдавал JPEG со знаком на сером фоне внутри белого круга.
`dalle-3` даёт самый внятный логотип за 7 ₽.

**Повторный кадр dalle-3 заказывается только при пустом знаке** (доля заливки ниже 2 %).
При исключении повтора нет: к этому моменту задача в GenAPI обычно уже выполнена и
оплачена — опрос не дождался ответа, не скачалась картинка, упала обработка. Раньше повтор
был на любую ошибку, и выходило два списания в GenAPI при ошибке у пользователя. Скачивание
кадра (и вектора) повторяется само: 3 попытки, таймаут 30 секунд, — оно бесплатное.

Настройки подобраны замером: `quality: standard` (hd стоит 14 ₽ и добавляет вредную для
логотипа детализацию), `style: natural`, приставка `KEEP_PROMPT` против переписывания промпта
самой моделью, цвета словами, а не hex.

**Фон снимается заливкой от краёв** (`rasterService`), а не порогом по яркости: прозрачным
становится только фон, связанный с границей кадра, цвет берётся медианой по краям. Порог не
справлялся с шумным фоном dalle-3 — оставался полупрозрачный светлый квадрат вокруг знака
(55 % полупрозрачных пикселей против ~1 % сейчас). Светлая деталь, касающаяся силуэта, всё
равно выпадает дырой: границы между ней и фоном физически нет.

**Перед обводкой картинка квантуется в 8 цветов без дизеринга**, а VTracer получает явные
настройки (`color_precision` 4, `layer_difference` 32, `filter_speckle` 10). На умолчаниях
двухцветный логотип превращался в 20 цветов и 19 путей, теперь — 3 и 3.

**Векторизация (`image-2-svg`, 1 ₽) принимает максимум 1024 px.** На 2048 и 3072 приходит
«Изображение не прошло модерацию контента» — это ограничение по размеру, а не по содержимому.
Перед обводкой кадр ужимается до 1024 и сводится на белый; фоновый path снимает санитайзер.
Файл уходит multipart-загрузкой, а не ссылкой: чистый логотип статикой не раздаётся.

**Цены в каталоге GenAPI врут.** `longcat-image` заявлен 0 ₽ — списал 65 ₽; `gpt-image-1`
2.5 → 33.65 ₽; `recraft` 8 → 15 ₽; `gpt-image-2` 22.5 → 10 ₽. Проверяйте реальным запросом.

**Разнообразие — структурой, как у названий.** Каталог приёмов в `backend/utils/logoPatterns.ts`,
пул приёмов и палитра стиля — в `STYLE_PROFILES`. Уже показанные приёмы и предметы приходят из
`logosRepo.recentConcepts()` и из `exclude` от клиента, иначе повторная генерация выдаёт то же самое.

**Кириллицу картинной модели не отдаём.** Название набирает `lockupService` шрифтом из образа,
поэтому буквы всегда правильные. Ширину слова у librsvg не спросить — `measure()` меряет её
рендером; поле по краям и сдвиг на половину `letter-spacing` обязательны, без них надпись
срезалась о край холста.

Водяной знак рисуется через SVG с текстом, поэтому образу нужны шрифты — `fontconfig` и
`fonts-dejavu-core` ставятся в стадии `base`. Без них `sharp` молча выдаёт пустой знак.

Файлы логотипа (все в одном каталоге `GENERATED_LOGOS_DIR`). Всё, где в имени есть
`-source`, статикой не отдаётся — только через роуты с проверкой оплаты:

| Файл | Что это | Кто видит |
|---|---|---|
| `<uuid>-preview.png` | 1024 px с вшитой плиткой PIXORA, это `logo_url` | все, до оплаты |
| `<uuid>-source.png` | чистый логотип 3072 px, `original_logo_url` | после оплаты, через роут |
| `<uuid>-source-original.png` | кадр модели без обработки, находится по имени (`rawNameFor`) | после оплаты, через роут |
| `<uuid>-source.svg` | вектор, появляется только после оплаты | после оплаты, через роут |
| `<uuid>-full.{png,svg}` | открытые копии для страницы оплаченного брендбука (`releaseSource()`) | владелец брендбука |
| `logo-<id>-mark-source.{png,svg}` | знак без надписи и его вектор — кэш для повторной сборки | внутри брендбука |
| `logo-<id>-<32 hex>-demo-{mono,inverted}.png` | ч/б и негатив превью для демо | все, до оплаты |
| `bb-<id>-<хвост>-<слот>-{source,preview}.*` | файлы брендбука: для архива и для страницы | владелец брендбука |

Раньше клиенту уходила прямая ссылка на чистую картинку, а водяной знак рисовался на фронте
поверх неё.

**Слаги сетей GenAPI пишутся через дефис и без точек** (`gpt-5-6-luna`, а не `gpt-5.6-luna`),
nano-тиров у него нет — неизвестное имя даёт 404 на POST. Актуальный список: `GET /api/v1/networks`.

Все вызовы идут через GenAPI по одной схеме: отправить задачу → получить `request_id` →
опрашивать `/request/get/{id}`, пока не готово. Опрос (`waitForResult`, до 60 попыток раз в
3 секунды) и разбор ответа (`extractTextFromResponse`) живут в одном месте —
`utils/apiUtils.ts`; второй копии в `nameService` больше нет. **Формат ответа у линеек
разный:** gpt-4o кладёт текст в `full_response[0].message.content`, линейка gpt-5 — в
`result[0].choices[0].message.content`, `apiUtils` знает оба.

### Сборка брендбука

Главный файл — `brandbookServices/brandbookBuilder.ts`, функция `buildBrandbook()`. Каталог
шагов и контракт прогресса — `brandbookServices/progress.ts`. Восемь шагов с весами, сумма 100:

```
1. палитра      5 %  крит.  → brand/paletteService     (от палитры логотипа, colord)
2. шрифты       3 %  крит.  → brand/typographyService  (каталог вендоренных шрифтов)
3. логотип     20 %  крит.  → brand/logoAssetService   (локапы + цветовые версии)
4. слоган       5 %         → sloganService            (gpt-5-6-luna)
5. иконки      10 %         → brand/iconSetService + brand/patternService
6. рекомендации 12 %        → content/guidelinesService (gpt-5-6-luna + фолбэк)
7. носители    20 %         → mockups/*                (визитка, соцсети, презентация, подпись)
8. PDF         25 %         → render/pdf + layout/pages (rsvg-convert)
```

Порядок обязательный: логотип берёт палитру и шрифты, рекомендации — всё собранное до них.

**Результат каждого шага пишется в строку `brandbooks` сразу** (`brandbooksRepo.patch`).
Раньше строка создавалась последней командой выдачи, и падение на любом этапе оставляло
оплатившего вообще без брендбука. Некритичный шаг при сбое помечается `failed` в
`build_steps`, и сборка идёт дальше; критичный уходит в `failDelivery`, и следующий опрос
повторит сборку. У каждого шага свой таймаут.

Что считает модель, а что код: **слоган и рекомендации — модель** (`gpt-5-6-luna`, оба
шага с запасным вариантом в коде на случай сбоя), **палитра и шрифты — код**, но не
угадыванием по ключевым словам, а от купленного логотипа: два цвета из
`generated_logos.palette` плюс производные через `colord`, и пара шрифтов по стилю с
приоритетом у шрифта надписи на логотипе. Носители собираются вектором в физических и экранных размерах. Иконки
подбираются офлайн из локального набора по словарю переводов русских слов на английские,
паттерны рисуются кодом из фирменных цветов.

**PDF собирается из полос, а не из HTML.** Каждая полоса — модуль в `layout/pages/`,
возвращающий строку SVG в миллиметрах (`width="297mm" viewBox="0 0 297 210"`), а
`render/rsvg.ts` отдаёт их все одной командой `rsvg-convert -f pdf`. Ширины строк для
переноса читаются из вендоренных ttf через `opentype.js`. Упавшая полоса выпадает из
документа, а не роняет заказ; полоса без содержимого отсекается ещё до нумерации
(`PageModule.enabled`), поэтому дыр в содержании не бывает. Замеры на трёх стилях (ещё до
полосы носителей): 14 полос, 160–215 КБ, 0.2–0.4 с, страница ровно A4-альбом 841.89 × 595.276 pt, текст в PDF
выделяется мышью (шрифты встроены, кириллица правильная).

Сборка идёт **вне HTTP-запроса** и занимает минуты. Ход виден клиенту: строка заводится до
начала сборки, а `build_step` / `build_progress` / `build_steps` обновляются по мере работы.
Очереди по-прежнему нет, повтор — только через опрос статуса заказа.

### Платежи — `yookassaService.ts`

Тонкий клиент API ЮKassa, без бизнес-логики:

- `createPayment()` — одностадийный платёж (`capture: true`) с `confirmation.type = redirect`
  и чеком. Способ оплаты не передаётся: его выбирает пользователь на форме ЮKassa
- `getPayment()` — состояние платежа из API. Это единственный источник правды о статусе
- `isNotificationIp()` — адрес отправителя уведомления против официального списка сетей

Ключи читаются лениво, при первом запросе. Раньше сервис создавался на импорте и падал
без ключей ЮKassa — вместе с ним не поднимался весь бэкенд.

Сетевые сбои и 5xx повторяются трижды с тем же `Idempotence-Key`: по нему ЮKassa вернёт
уже созданный платёж, а не заведёт второй. На 4xx повтора нет — такой запрос неверен сам
по себе. У каждого запроса таймаут 20 секунд.

## Как проходит покупка

Цены заданы на сервере в `services/orderService.ts` (`PRODUCTS`): логотип 299 ₽, брендбук
499 ₽. Клиент присылает только тип продукта, `logoId`, email и телефон для чека. Цену,
номер заказа, адрес возврата, `userId`, а также название, ключевые слова, слоган, нишу и
стиль сервер берёт сам — из записи логотипа. В оплаченный PDF не попадает текст из запроса.

Сценарий — **«Умный платёж»**
([документация](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/smart-payment)):
мы создаём платёж и уводим пользователя на форму ЮKassa, где он сам выбирает карту, СБП
или что-то ещё. Никаких `payment_method_data` мы не передаём и своего списка способов
оплаты не рисуем.

```
Клиент → POST /api/yookassa/create-payment { productType, productData: { logoId, email, phone } }
       → логотип ищется по logoId и req.user.id
       → запись согласия с офертой в user_consents
       → строка в payments со своим order_id (UUID), статус pending
       → POST в ЮKassa, Idempotence-Key = order_id
       → в payments проставляется yookassa_payment_id
       → редирект на confirmation_url
       → пользователь платит
       → ЮKassa возвращает его на /pages/payment/success?orderId=<order_id>
```

**Номер заказа — наш `payments.order_id`**, и он же уходит в `brandbooks.order_id`.
Раньше номеров было два (клиентский `order_<время>` и id платежа), они не совпадали, и
`UNIQUE` по `brandbooks.order_id` ничего не защищал.

### Выдача

Вся логика заказа после оплаты — в [services/orderService.ts](../backend/services/orderService.ts)
(`syncWithYookassa`, `deliverOrder`, `deliverLogo`, `deliverBrandbook`). Роут оплаты и фоновый
планировщик вызывают одни и те же функции. Выдачу запускают три пути:

1. **Вебхук** `POST /api/yookassa/webhook`.
2. **Опрос** со страницы успеха: `GET /api/yookassa/payment/:orderId`.
3. **Досборщик** в `jobs/scheduler.ts` (см. ниже).

Ни один из них не ждёт окончания выдачи — брендбук собирается минутами, а уведомлению
ЮKassa нужен быстрый `200`. Клиент опрашивает статус и видит прогресс.

Защита от двойной выдачи — **колонка `payments.delivery_status`**, ломать её нельзя:

- `paymentsRepo.claimDelivery()` одним `UPDATE … RETURNING` переводит заказ в `processing`
  и увеличивает `delivery_attempts`. Строку получает ровно один вызывающий, остальные —
  `null` и выходят.
- Условие захвата (`CLAIMABLE`) одно на захват и на выборку досборщика: `pending`; `failed`,
  если с прошлой попытки прошло **2 минуты**; `processing`, зависший дольше 20 минут. И во
  всех случаях `delivery_attempts < 5`.
- Пауза появилась потому, что раньше упавшая выдача повторялась **на каждом опросе** страницы
  успеха — раз в 3 секунды, пока открыта вкладка, — и стабильно падающая сборка жгла GenAPI.
- После 5 попыток автоповторы прекращаются, уходит алерт. Перезапуск вручную — в
  [run.md](run.md#оплачено-но-не-выдано).
- `UNIQUE` по `brandbooks.order_id` и `claimBuild()` остаются вторыми воротами для брендбука.

Каждая неудачная попытка шлёт алерт (`alertService`, письмо на `ALERT_EMAIL` или
`CONTACT_EMAIL`, одно письмо на ключ в час).

### Фоновые задачи

`jobs/scheduler.ts`, в том же процессе, что и API. Задача не запускается поверх самой себя.

| Задача | Как часто | Что делает |
|---|---|---|
| Довыдача | каждые 2 мин | Берёт заказы по `CLAIMABLE` и запускает выдачу. Подбирает и брошенные при перезапуске |
| Сверка свежих платежей | каждые 5 мин | Платежи в `pending` возрастом 3 мин – 2 ч сверяет с API ЮKassa. Нужна, когда уведомление потерялось, а покупатель ушёл со страницы успеха — раньше такой заказ висел навсегда |
| Сверка старых платежей | каждый час | То же для возраста 2 ч – 48 ч. Два ритма — чтобы брошенная оплата не давала сотни запросов к ЮKassa |
| Чистка | раз в сутки | Просроченные сессии и токены писем, записи лимитов по адресу старше недели, демо-файлы без ссылок старше суток. Неоплаченные логотипы старше 90 дней (`UNPAID_LOGO_RETENTION_DAYS`, 0 — не удалять). Логи (info — 14 дней, остальное — 60), метрики HTTP старше 30 дней, снимки баланса старше года, обращения старше года |
| Проверки состояния | каждые 5 мин | База, GenAPI и баланс, ЮKassa, SMTP, сертификат, диск. Сбой — алерт, снимок баланса — в `genapi_balance` |

Статус каждой задачи (последний запуск, длительность, ошибка, число сбоев) отдаёт
`schedulerStatus()` — его показывает мониторинг: молча упавший досборщик — это невыданные заказы.

**Неоплаченные логотипы удаляются через 90 дней** вместе со всеми файлами (превью, чистый
файл, кадр модели, вектор, демо). Срок записан в `/pages/privacy` и `/pages/personal-data`
(версия pdn `2026-10-08`) и показан в кабинете: меняя число, правьте и тексты с подъёмом
версии в `backend/legal.ts` и `app/lib/legal.ts`. Не удаляется логотип, на который
ссылается любой заказ, — даже неоплаченный pending. При удалении строка
удаляется первой, с повторной проверкой «не оплачен и ни один заказ не ссылается»; файлы
трогаются только если строка действительно удалена.

Найти оплаченные, но не выданные заказы: `delivery_status <> 'completed'` при
`status = 'succeeded'`, для этого есть частичный индекс `payments_delivery_idx`.

### Проверка уведомлений

**У вебхуков ЮKassa нет подписи.** Прежний `verifyWebhookSignature()` считал HMAC по
выдуманной схеме и при любом исходе возвращал `true`. Вместо него — то, что рекомендует
документация:

- IP отправителя сверяется с официальным списком сетей ЮKassa (`isNotificationIp`),
  посторонний адрес получает `403`. Работает благодаря `trust proxy` и тому, что Caddy
  отдаёт `/api/*` в бэкенд напрямую.
- Тело уведомления считается только сигналом: состояние платежа перезапрашивается через
  `GET /v3/payments/{id}`.
- `paymentMismatch()` сверяет ответ с заказом: `paid === true`, сумма и валюта равны цене
  товара, `metadata.orderId` равен номеру заказа. Последнее закрывает подстановку чужого
  id платежа в уведомление о заказе, у которого своего id ещё нет. Расхождение — выдача
  останавливается и уходит алерт.

Ответ на уведомление всегда `200`, кроме сбоя на нашей стороне: любой другой код
заставляет ЮKassa повторять уведомление сутки, и в случае нашей ошибки это как раз нужно.

Уведомления настраиваются вручную в личном кабинете ЮKassa:
`https://<домен>/api/yookassa/webhook`, события `payment.succeeded` и `payment.canceled`.
По шагам — в [run.md](run.md#юkassa-уведомления-о-платежах).

## Бесплатные генерации

По 5 генераций названий и 5 генераций логотипа на пользователя, окно 14 дней. Константа
`FREE_GENERATIONS` и вся работа со счётчиками — в `db/repositories/generationUsageRepo.ts`,
данные в таблице `user_generation_usage`.

- Поверх квоты аккаунта работают бюджет и лимит на адрес — см. «Защита от фарма».
- **Окно скользящее, а не календарное.** `reset_at` ставит первая генерация. Если ему больше
  14 дней, тот же SQL-запрос, что списывает попытку, обнуляет **оба** счётчика и начинает окно
  заново. `reset_at IS NULL` тоже считается истёкшим.
- `consume(userId, kind)` проверяет и списывает **одним SQL-запросом**
  (`INSERT … ON CONFLICT DO UPDATE … WHERE used < limit`). Раздельная проверка позволяла бы
  двум одновременным запросам пройти сверх лимита. `null` в ответе — лимит исчерпан,
  роут отдаёт `403` с `code: 'GENERATION_LIMIT'` и русским текстом ошибки.
- Списание идёт **до** обращения к модели, а `release()` возвращает попытку, если генерация
  упала: за наш сбой пользователь платить не должен.
- `reset(userId)` обнуляет оба счётчика и начинает новое окно; вызывается в `deliverOrder()` —
  после каждой успешной оплаты выдаётся ещё по 5 генераций. Ошибка сброса только логируется,
  выдача оплаченного заказа от неё не зависит.

Слабое место: попытка списывается и тогда, когда пользователь просто закрыл вкладку, не
дождавшись картинки, — вернуть её некому.

## Удаление аккаунта

`DELETE /api/auth/account` в одной транзакции:

- удаляет названия, логотипы, брендбуки, сессии, токены и продуктовые события (`app_events`);
- вычищает email, телефон и имя из `product_data` платежей, **сами платежи оставляет** — их обязан хранить оператор по 54-ФЗ;
- обезличивает строку в `users` и проставляет `deleted_at`.

Записи в `user_consents` сохраняются с отметкой об отзыве — это доказательство факта получения и отзыва согласия, ради которого журнал и заведён.

Уникальность email действует только среди живых аккаунтов, поэтому адрес сразу освобождается для повторной регистрации.

## Файлы на диске

Путь к папке сгенерированных картинок задан в одном месте — `backend/paths.ts` (переменная `GENERATED_LOGOS_DIR`). Оттуда его берут и `render/assets.ts` при записи, и `index.ts` при раздаче. В докере это общий volume, смонтированный и в `api`, и в `web`.

Неоплаченное чистится через 90 дней (см. «Фоновые задачи»), оплаченное лежит бессрочно, и
бэкапов ни базы, ни volume нет. Это слабое место, оно записано осознанно.

## Админка, мониторинг и аналитика

Всё под `/api/admin/*` за `requireAdmin`: обычная сессия плюс почта из `ADMIN_EMAILS`.
Список адресов в env, а не роль в базе: права не должны выдаваться запросом, который можно
случайно выполнить. Пустой список — админка закрыта для всех, сервер при этом стартует.
Ответы не кэшируются (`Cache-Control: no-store`).

### Модели в духе Django

`admin/resources.ts` описывает каждую модель: `from` (таблица с join), колонки списка с SQL,
поиск, фильтры, поля карточки, связанные таблицы (`inlines`) и действия. `admin/engine.ts`
по описанию строит список с поиском, фильтрами, сортировкой и страницами, карточку и CSV.

- **В SQL попадают только строки из описания.** Значение фильтра сверяется со списком опций,
  колонка сортировки — со списком колонок, поиск идёт параметром. Новую модель или фильтр
  добавляйте в `resources.ts`, роуты трогать не нужно.
- `hidden` — служебные поля карточки для условий `visible()` у действий. Условие проверяется
  и на сервере: кнопку могли нажать на устаревшей карточке.
- Каждое действие, удачное и нет (`<действие>:failed`), пишется в `admin_actions` вместе с
  введёнными полями и ответом. Выгрузка CSV тоже.
- CSV — точка с запятой и BOM, иначе русский Excel открывает его одной колонкой.

| Модель | Действия |
|---|---|
| Заказы | повторить выдачу (обнуляет попытки), пересобрать брендбук, сверить с ЮKassa, отправить письмо о готовности, вернуть деньги |
| Брендбуки | пересобрать, отправить письмо |
| Пользователи | подтвердить почту, сбросить квоту, подарить генерации, завершить сессии, заблокировать / разблокировать |
| Обращения | отметить обработанным / вернуть в новые |
| Генерации по адресам | заблокировать адрес |
| Блок-лист адресов | добавить, убрать |
| Согласия, логотипы (галерея), названия, события, действия админов | только просмотр |

Действия — в `admin/actions.ts`:

- **Повтор выдачи** обнуляет `delivery_attempts`, переводит заказ в `pending` и сбрасывает
  `build_started_at` у брендбука — иначе `claimBuild` взял бы сборку только через 20 минут.
  Заказ, который выдаётся прямо сейчас (`processing` моложе 20 минут), не трогается.
  Пересборка готового брендбука дополнительно ставит ему `failed`. Это заменило SQL из run.md.
- **Возврат** — полная сумма через `POST /v3/refunds` с чеком (без `receipt` ЮKassa отказывает),
  ключ идемпотентности `refund-<orderId>`. Галочка «закрыть доступ»: брендбуку ставится
  `payment_status = 'refunded'` (скачивание проверяет `completed`), логотипу — `is_paid = false`,
  если на него не ссылается другой оплаченный заказ без возврата. Сумма возврата хранится в
  `payments.refunded_amount`, аналитика вычитает её из выручки.
- **Подарок генераций** уводит счётчик в минус (`generationUsageRepo.grant`). Действует до
  конца текущего окна, потом счётчики обнулятся как обычно. Плашка квоты при остатке больше
  лимита не пишет «7 из 5».
- **Блокировка** ставит `users.blocked_at` и удаляет сессии — выкидывает сразу. Вход отвечает
  `403 ACCOUNT_BLOCKED`. Аккаунт из `ADMIN_EMAILS` заблокировать нельзя.
- **Блок-лист адресов** проверяется при регистрации и в `reserveFreeGeneration` (`403 BLOCKED`).
  Ключ тот же, что у лимита на адрес: IPv6 блокируется подсетью /64. Копия списка в памяти на минуту.

Ошибки ЮKassa админу показываются текстом (`502 ЮKassa: …`): без него непонятно, что делать.

`GET /api/admin/logos/:id/file?kind=source|raw` отдаёт админу чистый файл и кадр модели — они
закрыты от статики, а оценивать качество генерации по превью с плиткой неудобно.

### Настройки без деплоя

`services/settingsService.ts`, таблица `app_settings`, копия в памяти на 30 секунд:

| Ключ | Что делает | Умолчание |
|---|---|---|
| `freePaused` | Ставит бесплатные генерации на паузу (`503 FREE_PAUSED`) | нет |
| `dailyBudgetRub` | Суточный бюджет бесплатного, перекрывает env | `GENAPI_DAILY_BUDGET_RUB` |
| `yookassaFeePct`, `taxPct`, `monthlyFixedRub` | Ставки для расчёта прибыли в аналитике | 3.5 %, 6 %, 0 ₽ |
| `genapiBalanceAlertRub` | Порог алерта по балансу GenAPI | 300 ₽ |

### Учёт вызовов GenAPI

Все вызовы идут через `apiUtils.run(model, label, body)` — постановка задачи плюс опрос. Раньше
каждый сервис делал `axios.post` сам, и учёт пришлось бы вставлять в пять мест. `run` пишет в
`genapi_calls` модель, что делал вызов, успех, длительность и смету по `MODEL_COST_RUB`
(`limits.ts`). Вызовы внутри выдачи заказа получают `order_id` через `AsyncLocalStorage`
(`withOrderContext` в `startDelivery`) — так видна себестоимость оплаченного отдельно от
бесплатного. Сбой записи метрики генерацию не роняет.

**Смета — не списание.** Реальные траты видны по снимкам баланса: проверка раз в 5 минут
читает `GET /api/v1/user` у GenAPI (поле `balance`) и пишет его в `genapi_balance`. Разница
соседних снимков — списание, рост — пополнение. Аналитика сравнивает их со сметой и
предупреждает, если расхождение больше 30 %.

### Мониторинг

- **Метрики HTTP** (`monitoring/httpMetrics.ts`) копятся в памяти по минуте, методу и шаблону
  маршрута (`/api/download-logo/:logoId`, а не настоящий путь) и раз в минуту сливаются в
  `http_metrics` сложением. Время — гистограммой по корзинам 50 мс … 60 с, из неё считаются
  перцентили с точностью до границы корзины. Поэлементного сложения массивов в Postgres нет —
  отсюда `unnest … WITH ORDINALITY` в запросах.
- **Проверки** (`monitoring/checks.ts`) — база, GenAPI с балансом, ЮKassa (`GET /v3/me`), SMTP
  (`verify`), сертификат (TLS-подключение к своему домену, как браузер), свободное
  место. `fail` — алерт. Результаты держатся в памяти, после перезапуска их нет до первого
  прогона (через 20 секунд). В админке есть кнопка «Проверить сейчас».
- **Алерты** — письмом, как и раньше, не чаще раза в час на повод. О сбое самой почты письмо
  не уйдёт, но строка `[ALERT]` остаётся в логах и видна в мониторинге в «Последних алертах».
- Обзор показывает состояние семафора логотипов, идущие выдачи, бюджет за сегодня, фоновые
  задачи, память, нагрузку, диск, размер картинок, базы и самых больших таблиц.

**Чего нет:** проверки снаружи. Мониторинг живёт в том же процессе, и если сервер лёг
целиком, он молчит.

### Аналитика

`admin/analytics.ts`, периоды — календарные дни по Москве. Всё считается из своих таблиц,
сторонних счётчиков нет.

- **Итоги и сравнение с прошлым периодом той же длины**: выручка за вычетом возвратов,
  прибыль после комиссии, налога, GenAPI и постоянных расходов, заказы, средний чек,
  регистрации, посещения.
- **Юнит-экономика**: стоимость активного бесплатного пользователя (смета GenAPI на бесплатное /
  число сделавших хоть одну генерацию), себестоимость заказа, маржа, **порог окупаемости
  конверсии против фактической** — главный вопрос модели «бесплатная квота → покупка».
- **Воронка** зарегистрировавшихся за период: подтвердили почту → сделали логотип → перешли к
  оплате → оплатили → купили повторно, сбоку — названия, предпросмотр брендбука, брендбук.
- **Источники**: посещения, регистрации, покупатели и выручка когорты по источнику.
  Источник первого касания приходит с регистрацией (`users.signup_source`).
- **Квота**: распределение пользователей по числу логотипов и доля купивших на каждом, отказы
  по причинам, сколько упёрлись в квоту и купили после, медиана времени и числа логотипов до
  первой покупки.
- **Оплата**: брошенные оплаты и список ушедших с отметкой согласия на рассылку, апсейл
  логотип → брендбук, возвраты.
- **Стили, приёмы и ниши** с долей оплаченных; **недельные когорты**: активация, возврат,
  покупка за 7 и 30 дней, выручка.
- **Выводы словами** — окупается ли бесплатное, продаёт ли стена квоты, расходится ли смета с
  балансом.

Слабые места:

- Неоплаченные логотипы удаляются через 90 дней, а событий `logo_generated` до этой версии
  нет. Число генераций — большее из двух источников по каждому пользователю; для периодов
  старше 90 дней генераций меньше, а конверсия по стилям выше, чем было на самом деле.
- Посещения считаются без идентификатора посетителя: сессия — это вкладка
  (`sessionStorage`). «Посещение → регистрация» поэтому приблизительно.
- Себестоимость — смета по `MODEL_COST_RUB`, реальное списание — только по балансу и только
  целиком, без разбивки по вызовам.
- Аналитика считается живыми запросами при каждом открытии. На тысячах пользователей это
  нормально; на сотнях тысяч понадобятся предрасчёты.
