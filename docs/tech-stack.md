# Технологии и как всё устроено

Из чего собран проект, зачем каждая зависимость и как части связаны между собой. Подробные
карты кода — в [backend.md](backend.md) и [frontend.md](frontend.md), запуск — в
[run.md](run.md), деньги и лимиты — в [economics.md](economics.md).

## Коротко

- **Два приложения в одном репозитории:** сайт на Next.js ([app/](../app/)) и API на Express
  ([backend/](../backend/)). Общего кода у них нет — только база и префикс `/api`.
- **Язык — TypeScript везде.** Строгий режим (`strict`) выключен и во фронте, и в бэкенде.
- **База — PostgreSQL 16**, без ORM, SQL пишется руками в репозиториях.
- **Нейросети — через GenAPI** (российский агрегатор), напрямую в OpenAI не ходим.
- **Оплата — ЮKassa**, почта — **Яндекс Cloud Postbox**, сертификаты — **Let's Encrypt** через Caddy.
- **Всё запускается в Docker Compose**: один файл, профили `dev` и `prod`.
- Проект рассчитан на **российский сервер без VPN**: шрифты и иконки лежат у нас, при сборке
  образа и брендбука ничего не скачивается из-за рубежа.

## Схема

```
                 Браузер
                    │  https://pixora-ai.ru
                    ▼
        ┌───────────────────────┐
        │ Caddy (только прод)   │  HTTPS, сертификат, заголовки безопасности, CSP
        └───┬───────────────┬───┘
   /api/*,  │               │  всё остальное
   /generated-logos/*       ▼
            │        ┌──────────────┐
            │        │ web: Next.js │  страницы сайта, порт 3000
            │        └──────────────┘
            ▼
     ┌───────────────┐        ┌──────────────────────────┐
     │ api: Express  │ ─────► │ GenAPI (нейросети)       │
     │ порт 3001     │ ─────► │ ЮKassa (оплата)          │
     │ + планировщик │ ─────► │ Postbox (письма, SMTP)   │
     └──┬─────────┬──┘        └──────────────────────────┘
        │         │
        ▼         ▼
  ┌──────────┐  ┌───────────────────────────────┐
  │ Postgres │  │ volume generated-logos        │
  │ (db)     │  │ картинки, PDF, архивы          │
  └──────────┘  └───────────────────────────────┘
```

- **В проде** `/api/*` и `/generated-logos/*` Caddy отдаёт в `api` напрямую, минуя Next:
  иначе терялся бы настоящий IP пользователя, а он пишется в журнал согласий и нужен
  лимиту на адрес.
- **В деве** Caddy нет: браузер ходит на Next (`:3000`), и тот проксирует `/api/*` в бэкенд
  через `rewrites` в [next.config.js](../next.config.js).
- Фоновые задачи (довыдача заказов, сверка платежей, чистка) живут **в том же процессе**,
  что и API, отдельного воркера нет.

Как устроено:

- Страницы лежат в `app/pages/…` — это **обычная папка**, она становится частью адреса
  (`/pages/logo-generator`), а не старый Pages Router.
- **Нет библиотек для данных и состояния** (Redux, React Query и т. п.). Запросы — обёртка над
  `fetch` в `app/lib/authClient.ts`, состояние между шагами — только в адресной строке.
- **Шрифт сайта системный.** `next/font/google` убран: он скачивает шрифты при сборке, а с
  российского сервера это падает.
- Метаданные для поисковиков — в `layout.tsx` страницы (помощник `pageMetadata()`), у лендингов и блога — прямо в `page.tsx`. Карта сайта — `app/sitemap.ts`, картинка превью ссылок — `app/og.png/route.tsx` (`next/og`, рисуется при сборке).
- Аналитики и трекеров нет, единственные cookie — сессионные.

## База данных

- **PostgreSQL 16** в контейнере `db`, наружу открыт только на `127.0.0.1`.
- Миграции — пронумерованные `.sql` в [db/migrations/](../db/migrations/). Их применяет
  отдельный контейнер `migrate` при каждом запуске и завершается; приложение ждёт его успеха.
  Уже применённые файлы не правим — только новые.
- Доступ к данным — через репозитории в `backend/db/repositories/`, по файлу на таблицу.
  Репозиторий владеет SQL и переводит `snake_case` в `camelCase`.
- Атомарность там, где важны деньги, держится **одиночными SQL-запросами**
  (`INSERT … ON CONFLICT … WHERE`, `UPDATE … RETURNING`): списание квоты, лимит на адрес,
  захват выдачи заказа.
- Полный список таблиц — в [backend.md](backend.md#таблицы-в-базе).

Асинхронно: создать задачу, опрашивать результат | Генерации отвечают ошибкой, попытка возвращается. Сборка брендбука упадёт на логотипе и повторится досборщиком |

| **Яндекс Вебмастер, Google Search Console, Bing Webmaster** | Индексация, ошибки, запросы, по которым приходят | Подтверждение мета-тегами в `app/layout.tsx` (`verification`) или записью DNS. Настройки ручные, см. [run.md](run.md#поисковики-и-indexnow) | Сайт работает, мы просто не видим статистики поиска |
| **IndexNow** (`api.indexnow.org`) | Быстрая переиндексация новых страниц в Яндексе и Bing | Ключ в `public/`, адреса отправляются вручную одной командой | Новые страницы найдутся по sitemap, но дольше |

Как устроен вызов GenAPI:

```
POST /api/v1/networks/<слаг>   → { request_id }
GET  /api/v1/request/get/<id>  → повторять раз в 3 секунды, пока status не success
```

Постановка, опрос и разбор ответа — в одном месте, `apiUtils.run()` в
[backend/utils/apiUtils.ts](../backend/utils/apiUtils.ts); там же каждый вызов пишется в
`genapi_calls` для мониторинга и экономики. Баланс читается из `GET /api/v1/user` (поле `balance`) —
в документации GenAPI этого нет, найдено перебором; если GenAPI его переименует, проверка
баланса в мониторинге станет красной.
Текстовые вызовы идут через [llmJson.ts](../backend/utils/llmJson.ts), который возвращает
`null` вместо исключения — у каждого вызова есть запасной вариант в коде.

Почта: домен отправителя из `MAIL_FROM` должен быть подтверждён в Postbox. Письма собраны
на инлайновых стилях, без внешних картинок и шрифтов.

## Docker

Один [Dockerfile](../Dockerfile) со стадиями, один [docker-compose.yml](../docker-compose.yml)
с профилями.

| Стадия | Для чего |
|---|---|
| `base` | Node 20 + системные пакеты + шрифты брендбука |
| `deps` / `prod-deps` | Все зависимости / только рантайм |
| `web-dev`, `api-dev` | Дев: код монтируется с хоста, зависимости лежат в `/node_modules` |
| `web` | Прод фронта: standalone-сборка Next |
| `api` | Прод бэкенда: скомпилированный JS из `backend/dist`, миграции, шрифты |

| Сервис compose | Профиль | Что делает |
|---|---|---|
| `db` | оба | Postgres 16, данные в volume `pgdata` |
| `migrate` | оба | Применяет миграции и завершается |
| `web-dev`, `api-dev` | dev | Сайт на :3000 и API на :3001 с перезапуском при правках |
| `web`, `api` | prod | То же в боевом виде, `api` с healthcheck и 60 секундами на остановку |
| `caddy` | prod | HTTPS и маршрутизация, порты 80 и 443 |

Volumes: `pgdata` (база), `generated-logos` (все картинки, PDF и превью — общий для `api` и
`web`), `caddy-data` и `caddy-config` (сертификаты). `docker compose down` их не удаляет.

Контейнеры работают от пользователя `node`, поэтому временные файлы пишутся в `/tmp`, а не в `/app`.

## Как всё работает: путь пользователя

1. **Регистрация.** Email + пароль, галочка согласия на ПДн. Пароль хешируется argon2id,
   согласие пишется в журнал с IP. Письмо со ссылкой уходит через Postbox; войти можно
   только после подтверждения.
2. **Сессия.** Две `httpOnly`-куки: короткий access-JWT и refresh-токен. Каждый защищённый
   запрос сверяет сессию с таблицей `sessions`, поэтому выход срабатывает сразу.
3. **Названия.** Форма на главной → `POST /api/generate-names`. Сервер проверяет бюджет,
   квоту и лимит на адрес, делает три параллельных вызова `gpt-5-6-luna` и отдаёт шесть
   названий с пояснениями.
4. **Логотип.** `POST /api/generate-logo`: модель придумывает концепцию → `dalle-3` рисует
   знак → sharp убирает фон → сервер набирает название шрифтом и собирает SVG → рендерит
   чистый PNG и превью с водяным знаком. Клиент получает **только превью**.
5. **Предпросмотр брендбука.** Статичная страница: структура разделов PDF с заглушками,
   без обращений к серверу и моделям.
6. **Оплата.** Сервер заводит заказ со своим номером и ценой, создаёт платёж в ЮKassa и
   отправляет пользователя на её форму. Там он выбирает способ оплаты.
7. **Выдача.** Уведомление ЮKassa, опрос со страницы успеха или фоновый досборщик
   запускают выдачу. Сервер перепроверяет платёж через API ЮKassa, захватывает заказ одним
   SQL-запросом (двойной выдачи не бывает) и:
   - для логотипа — строит вектор через `image-2-svg` и открывает скачивание;
   - для брендбука — проходит восемь шагов: палитра → шрифты → версии логотипа → слоган →
     иконки → рекомендации → носители → PDF через `rsvg-convert`. Каждый шаг сохраняется
     сразу, ход сборки виден на странице.
8. **Письмо «брендбук готов»** и скачивание одним ZIP через `/api/download-brandbook`.

## Слабые места

- **Один сервер, один процесс API.** Сборка брендбука, генерации и фоновые задачи делят один
  процессор. Очереди задач нет — защищает только семафор на логотипы.
- **Бэкапов нет** — ни базы, ни volume с картинками.
- **Мониторинг живёт внутри того же процесса.** Если сервер лёг целиком, ни проверки, ни алерты
  не сработают, а проверки снаружи нет. Метрики, логи и аналитика хранятся в той же базе, что и
  заказы.
- **Графики админки — свой SVG**, без библиотеки: меньше зависимостей, но и возможностей
  (масштабирования, выгрузки картинкой) нет.
- **Нет тестов**, единственная проверка — типы, и та без `strict`.
- **Зависимость от одного поставщика нейросетей.** Если GenAPI недоступен или кончился
  баланс, не работает ни одна генерация.
- **Пакет `uuid` в зависимостях не используется** — идентификаторы делает встроенный
  `crypto.randomUUID()`. Его и `@types/uuid` можно убрать.
- **Типы React отстают от самого React**: `react` 19, а `@types/react` и
  `@types/react-dom` — 18.
- Метрики текста у вариативных шрифтов приходится поправлять коэффициентами (`WIDTH_FACTOR`):
  `opentype.js` не применяет вариации к ширине.
